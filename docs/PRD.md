# PRD: Pathawk — HTTP-клиент и платформа для API (аналог Postman для рынка РФ)

**Версия документа:** 0.11  
**Дата:** 2026-04-30  
**Статус:** продуктовые решения по §11 согласованы; **календарные даты намеренно не фиксируются** (ориентир ~6 мес., см. §11)

**Имя продукта:** **Pathawk**

- **Написание:** в интерфейсе и продуктовой документации — **Pathawk**; в CLI, именах репозиториев и пакетов — **`pathawk`** (нижний регистр).
- **Произношение:** англ. *path* + *hawk* (ударение на первый слог: /ˈpæθ.hɔːk/); русская диктовка — **«пасхок»** (единый вариант в README и на сайте).

---

## 1. Резюме

**Pathawk** — клиент и экосистема для отладки и совместной работы с **HTTP API** и **WebSocket**, ориентир по возможностям — **долгосрочный паритет с Postman**, с поэтапной поставкой.

**Отличия для рынка РФ (питч):**

- нормальная **работа в РФ** (продукт и платежи не «отваливаются» из‑за внешних ограничений);
- **оплата картами РФ** — для всех сценариев монетизации (облако у поставщика, лицензии, self-hosted — по мере появления офферов);
- **развёртывание в контуре компании**: несколько схем — **сервер у заказчика + десктоп** (образ/пакет под политики Заказчика) и сценарий **через Git** (в т.ч. Git на своём сервере у компании).

**Первая значимая версия (v1)** — не полный паритет с Postman: без **тестов в коллекциях** и **моков** (перенос на **v2**), без **плагина IDE** ( **v2**). Протоколы **gRPC** и отдельный режим **GraphQL** — после v1.

**Офлайн:** полноценная работа без связи с серверами поставщика обязательна (локальные данные + Git).

**Команда и горизонт:** ориентир **~6 месяцев** до первой публичной версии; **1 разработчик + ИИ-агенты**; **календарная дата** не зафиксирована.

**Публичный v1 (готовность):** в **одном** публичном релизе поставляются **десктоп-клиент** и **разворачиваемый у заказчика сервер** с **шарингом коллекций** (роли — позже); отдельного релиза «только десктоп без сервера» для объявления v1 **не планируется**.

## 3. Персоны и сценарии

### 3.1 Персоны (приоритет)

- **Разработчик (фронт/бэк)** — запросы, окружения, коллекции, импорт спецификаций.
- **QA** — воспроизведение сценариев, наборы запросов, обмен коллекциями.

Сценарии **«только я»** и **«команда»** важны **примерно поровну** с ранних релизов.

### 3.2 Пользовательские истории — v1 (инкремент 1)

1. Собрать и отправить **HTTP**-запрос; увидеть статус, время, заголовки, тело; типы body как у класса Postman (JSON, form, raw, binary и т.д.).
2. Работа с **WebSocket** (подключение, обмен сообщениями — детали реализации в спецификации v1).
3. **Окружения** и переменные; подстановка в URL, заголовки, тело.
4. **Коллекции** и папки; экспорт/импорт; **импорт и экспорт OpenAPI**; **совместимость с Postman Collection** (импорт/экспорт — уточнить версию v2.1 в техническом ТЗ).
5. **История** запросов локально; понятно, где хранятся данные.
6. **Офлайн:** работа без доступа к облаку поставщика.
7. **Интеграция с Git:** коллекции/артефакты в репозитории; клиентский Git может быть на сервере компании.
8. **Шаринг коллекций** — в v1; **без ролевой модели на первом этапе** (роли — последующий инкремент).
9. Интерфейс: **RU + EN** с первой значимой версии.

### 3.3 Исключено из v1 (явно)

- Скрипты **tests** / **pre-request** в стиле Postman, визуальный тест-раннер — **v2**.
- **Мок-сервер** / фикстуры ответов — **v2**.
- **Плагин IDE** — **v2**.
- **gRPC**, отдельный режим **GraphQL** — после v1.
- Каталоги пресетов под отечественные API (банки, гос. сервисы) — **roadmap**, не v1.
- **CLI** для CI/CD — **не приоритет** в обозримом горизонте.

### 3.4 Командный сервер (когда появляется)

- Аутентификация: **SSO (SAML и/или OIDC)**; вход через **Яндекс и другие OAuth**-провайдеры.
- **Журнал аудита** для администраторов (действия с коллекциями, входы, экспорт — перечень событий в отдельном документе).
- Схема поставки: **сервер в контуре Заказчика** + **десктоп** (дистрибутив/образ по политикам Заказчика).

**Шаринг коллекций в v1 (без ролей):**

- **Приглашение по email:** пользователь указывает адрес (типично **корпоративная почта** коллеги; допускается и «публичная» почта, как в привычных SaaS); получатель проходит поток принятия (ссылка из письма / вход на сервер — детали в ТЗ).
- **Публичный доступ «как в Postman»:** возможность выдать **публичную ссылку** на коллекцию (или эквивалентный механизм) для просмотра/импорта без перечисления email — с политиками безопасности (срок жизни ссылки, отзыв — в ТЗ).

Доставка писем на self-hosted инстансе: настройка **SMTP** (или иной канал уведомлений) администратором — **инженерное ТЗ / эксплуатация**.

**Роли (viewer/editor/admin и т.д.):** не в первом этапе шаринга; добавляются после простого шаринга.

## 4. Объём продукта по версиям

### 4.1 Версия 1 (первая значимая)

- HTTP/HTTPS (методы, редиректы, таймауты, отмена).
- WebSocket.
- Авторизации и заголовки — паритет с ожиданиями класса Postman (детализация в ТЗ).
- Коллекции, окружения, переменные; локальное хранилище; **офлайн**.
- Импорт/экспорт **OpenAPI**; работа с **Postman Collection**.
- Git-first workflow опционально; шаринг коллекций (механика — ТЗ), **без ролей в первом этапе**.
- Десктоп **минимум** для v1 (**Electron** + общий UI); **веб** — тот же **Vue 3** UI, поставка после или параллельно с десктопом (планирование).

### 4.2 Версия 2 (следующий крупный шаг)

- Тесты в коллекциях, pre-request, раннер (по возможности совместимый с привычками Postman).
- Моки.
- Плагин для IDE (например VS Code / JetBrains — уточнить).
- gRPC; GraphQL при необходимости.
- **Портал документации** из коллекции (read-only / публикация для команды или наружу — детали в ТЗ): **желателен в v2**, **не блокер** релиза v2; при нехватке ресурсов **допускается перенос на v2.x** после ядра v2 (тесты, моки, IDE, протоколы).

### 4.3 Не в scope без отдельного решения

- Публичный маркетплейс плагинов без модели безопасности.
- Плановый облачный мониторинг расписаний «как Postman Monitor» — только если появится запрос.

## 5. Данные и развёртывание

- **Источник правды:** устройство пользователя и/или **Git** (в т.ч. **сервер Git у компании**). Публичное облако поставщика с коллекциями клиентов **не является** обязательной центральной моделью.
- Поддерживаются **несколько схем:** self-hosted **сервер продукта** + десктоп; обмен через **Git** без обязательного сервера поставщика.

## 6. Нефункциональные требования

### 6.1 Офлайн и прозрачность

- Работа без связи с облаком поставщика; явное объяснение в UI/docs, куда сохраняются коллекции и секреты.

### 6.2 Безопасность

- Маскирование секретов в UI/логах по умолчанию; без утечки в сторонние аналитики без согласия.
- Обновления десктопа — подписанные каналы (когда дистрибуция будет определена).

### 6.3 Соответствие (РФ)

- **Приоритет продукта:** функционал.
- При проектировании хранения ПДн ориентир — **152-ФЗ** (юридическая проработка отдельно). **Внесение в реестр отечественного ПО** и **сертификация** ФСТЭК/ФСБ — **не целевой трек на текущей фазе**; рассматриваются **только по запросу** заказчика (тендер, политика закупок). «Только РФ» для всех сервисов — не зафиксировано для v1.

### 6.4 Локализация

- **RU** по умолчанию, **EN** в v1.

### 6.5 Корпоративные сети

- Системный прокси, корпоративные CA — высокий приоритет для B2B (конкретизация по мере пилотов).

## 7. Платформа и технологический стек

### 7.1 Состав (зафиксировано)

| Слой | Выбор | Назначение |
|------|--------|------------|
| **UI** | **Vue 3** | Единый интерфейс для десктопа и (далее) веб-клиента |
| **Десктоп-оболочка** | **Electron** | Win / macOS / Linux, доступ к ФС, автообновления (политика позже) |
| **Командный сервер** | **Go** | API синхронизации, SSO/OAuth-обвязка, аудит, on-prem деплой |
| **СУБД сервера** | **PostgreSQL** | Пользователи, метаданные коллекций, аудит и т.д. (детальная схема — в ТЗ) |
| **Локальное хранилище (десктоп)** | **bbolt** в составе **локального Go-процесса** | Офлайн, коллекции и связанные данные; встраиваемое KV в одном файле; связь UI — через **IPC / локальный HTTP** к процессу на Go (детали в ТЗ) |

Локальный слой на **Go** поставляется вместе с **Electron**-оболочкой (вложенный бинарь / sidecar). Требования PRD (**офлайн**, **Git** через экспорт/файлы при необходимости) сохраняются: поверх bbolt остаётся **импорт/экспорт** в открытые форматы.

### 7.2 Платформа и дистрибуция

| Компонент | Статус |
|-----------|--------|
| Десктоп Win/macOS/Linux | **Обязателен** для v1 (**Electron** + Vue 3) |
| Веб | Тот же **Vue 3**; срок относительно v1 — в плане разработки |
| Плагин IDE | **v2** |

### 7.3 Организация кода (репозитории)

Исходники ведутся в **трёх отдельных git-репозиториях**: **бэкенд** (Go + PostgreSQL), **фронт** (Vue 3, общий UI), **десктоп** (Electron + вложенный **local-agent** на Go). Детали и связи — в [TECH_SPEC.md](./TECH_SPEC.md) §1 и [README.md](./README.md).

## 11. Открытые решения

**Закрыто:**

- **T1** — стек: **Vue 3** (общий UI), **Electron** (десктоп), **Go** (командный сервер), **PostgreSQL** (см. §7).
- **T2 (определение «готово к публичному v1»):** в составе v1 — **десктоп** (полный клиентский функционал v1) **и** **self-hosted сервер** с **шарингом** коллекций **без ролей** на первом этапе; сервер включает зафиксированные ранее **SSO (SAML/OIDC)**, **OAuth (Яндекс и др.)**, **аудит**.
- **T3 (механика шаринга v1):** **приглашения по email** (корпоративная или личная почта) **и** **публичная ссылка** на коллекцию в духе Postman; детали прав (только чтение / импорт) и отзыв — в ТЗ (см. §3.4).
- **T4 (портал документации):** **желателен в v2**, приоритет **после** основного объёма v2; **можно сдвинуть** на v2.x при ограничении ресурсов (см. §4.2).
- **T5 (реестр ПО / сертификация):** **не актуально** как обязательная цель сейчас; **только по запросу** заказчика (см. §6.3).
- **T2a (календарь релизов):** **без фиксации** дат альфы/беты/публичного v1; ориентир **~6 месяцев** и состав команды — как в **§1**; даты появятся при планировании спринтов.
- **T6 (локальное хранилище десктопа):** **bbolt** в **локальном Go-процессе**, в связке с Electron (см. §7.1).
- **T7 (имя продукта):** **Pathawk**; написание **Pathawk** / **`pathawk`** (CLI) и произношение — в шапке документа.

**Открытых позиций по §11 не осталось**; дальнейшие уточнения — в инженерном ТЗ и спринт-планировании.

## 12. Roadmap (согласовано с интервью)

1. **v1 (единый публичный релиз):** **десктоп** + **self-hosted сервер**; HTTP + WebSocket; коллекции; окружения; OpenAPI + Postman Collection; Git; офлайн; шаринг **без** ролей: **email-приглашения** + **публичная ссылка** (в духе Postman); RU+EN; сервер: SSO (SAML/OIDC), OAuth (Яндекс и др.), аудит.
2. **v2:** тесты/pre-request, моки, плагин IDE; gRPC/GraphQL по приоритету; **портал документации** — желательно, **после** ядра v2 или в v2.x (см. §4.2).
3. **Будущее:** пресеты/каталоги под отечественные API; CLI для CI при смене приоритета.

## 13. Критерии приёмки v1 (высокий уровень)

- За ≤10 минут новый пользователь отправляет успешный запрос с переменными окружения.
- Импорт **OpenAPI** и **Postman Collection** не ломает структуру папок в типичных кейсах (список эталонных файлов в QA).
- WebSocket: установление соединения и обмен сообщениями в согласованном сценарии smoke-теста.
- Работа **офлайн** после первого запуска для локально сохранённых коллекций.
- **Self-hosted сервер** разворачивается по инструкции (Docker/бинарь + PostgreSQL — конкретика в ТЗ); smoke: вход (в т.ч. согласованный OAuth/SSO-поток), аудит пишет события.
- **Шаринг коллекции** end-to-end через сервер (**без ролей** на первом этапе): сценарий **приглашения по email** и сценарий **публичной ссылки** (как в Postman); отзыв/истечение ссылки — по ТЗ.
- Нет отправки секретов во внешнюю аналитику по умолчанию.
